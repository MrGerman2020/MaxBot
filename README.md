# Мой дом — чат-бот ЖКХ в мессенджере MAX

Чат-бот для жителя многоквартирного дома: принимает обращение в мессенджере,
**сам отправляет письмо в управляющую организацию** и **возвращает ответ УК в тот
же чат**. Дополнительно распознаёт фото протокола и квитанции.

Работает на официальной библиотеке MAX, хранит историю в SQLite и не требует
от жителя ни приложений, ни регистрации.

---

## 1. Назначение решения

Житель не должен разбираться, куда и как писать в управляющую организацию, и
не должен терять ответ. Решение закрывает три разрыва:

| Разрыв | Как закрыт |
|---|---|
| Непонятно, куда писать | Бот сам формирует письмо по требованиям ст. 7 59-ФЗ и отправляет на email УК |
| Ответ приходит мимо мессенджера | Бот опрашивает свой ящик по IMAP и возвращает ответ УК в чат |
| Заявка теряется | Каждое обращение получает номер, категорию, адрес, статус и историю отправки |

Канал доставки один из трёх, и все три доступны из карточки обращения:

1. **Бот в MAX** — основной автоматический канал (письмо уходит из чата).
2. **Электронная почта УК** — рабочий юридический канал по ст. 11 ЖК РФ.
3. **Официальный сайт** — «Госуслуги Дом» и личный кабинет ГИС ЖКХ.

Прямая отправка в ГИС ЖКХ невозможна: API РИАС ЖКХ выдаёт токен только
зарегистрированной организации, а схема импорта обращений требует
идентификатор самой организации. Обоснование — в `docs/ЖКХ_API.md`.

## 2. Основной пользовательский сценарий

Житель пишет боту в MAX обычным текстом и кнопками.

```
/start
  └─ 📝 Подать обращение
       ├─ адрес дома          ← кнопка «Использовать сохранённый» или текстом
       ├─ категория из шести   ← кнопками: 🚰 Сантехника, ⚡ Электрика,
       │                        🔥 Отопление, 🧹 Уборка, 🏗 Капремонт, 📄 Прочее
       ├─ текст проблемы      ← свободным текстом
       ├─ ФИО и свой email     ← из профиля «⚙️ Мои данные» или вводом
       ├─ email УК             ← кнопкой, если он уже сохранён
       └─ ✅ Обращение №12 отправлено
              │
              ├─ УК отвечает на письмо
              ├─ бот забирает письмо из ящика (раз в 5 минут)
              └─ 📬 Ответ по обращению №12 → в тот же чат
```

Параллельно доступны: «📋 Мои обращения» (номера, статусы, повторная отправка,
жалоба в ГЖИ), «📬 Ответы УК», «⚙️ Мои данные», «🗳 Проверить протокол» по фото,
«💰 Начисления и капремонт» по фото квитанции.

Кнопка «🏠 Главная» присутствует в **каждом** сообщении — выйти из любого
экрана можно одним нажатием.

## 3. Состав и архитектура решения

Локальный компонент **один** — процесс бота. HTTP-сервера нет: бот работает на
long polling к API MAX. База данных — не сервис, а файл SQLite.

```
                        ┌──────────────────────────────┐
    MAX  ◄── long ────► │  bot.py                      │
   (мессенджер)  polling │   ├─ handlers/appeals.py     │  сценарии диалога
                        │   ├─ handlers/votes.py       │  протоколы ОСС
                        │   ├─ handlers/charges.py     │  начисления
                        │   ├─ handlers/start.py       │  приветствие, меню
                        │   ├─ services/uk_delivery.py │  сборка и отправка письма
                        │   ├─ services/uk_inbox.py    │  приём ответов по IMAP
                        │   ├─ services/ocr.py         │  распознавание фото
                        │   ├─ services/rias_api.py    │  чтение ГИС ЖКХ
                        │   ├─ scheduler.py            │  опрос ящика
                        │   ├─ keyboards.py            │  клавиатуры
                        │   └─ database.py             │  SQLite, 7 таблиц
                        └───────────┬──────────────────┘
                                    │
                          SQLite: ./data/zhkh.db
                          (bind-mount, виден на хосте)
                                    │
              ┌─────────────────────┴─────────────────────┐
              │                                           │
        SMTP 465 ──► УК (письмо)              IMAP 993 ◄── УК (ответ)
              │                                           │
              └──────► письмо УК возвращается в MAX ◄─────┘
                            через uk_inbox + scheduler
```

Разделение ответственности:

| Слой | Файл | Что делает |
|---|---|---|
| Точка входа | `bot.py` | инициализация базы, роутеры, планировщик, polling |
| Настройки | `config.py` | читает `.env`, отдаёт остальному коду значения |
| Диалог | `handlers/` | состояния и сценарии, вся работа с пользователем |
| Внешние системы | `services/` | почта, IMAP, OCR, РИАС ЖКХ |
| Хранение | `database.py` | асинхронный SQLite, аддитивные миграции |
| Фоновые задачи | `scheduler.py` | периодический опрос ящика с ответами УК |
| Клавиатуры | `keyboards.py` | все кнопки, включая гарантированную «Главная» |
| Обслуживание | `tools/seed_test_data.py` | подложить или убрать тестовое обращение |

## 4. Запуск: одна команда

```bash
docker compose up -d --build
```

Это всё, что нужно: compose соберёт образ, создаст каталог `./data`,
поднимет бота и подставит переменные из `.env`.

Проверить, что он поднялся:

```bash
docker compose logs -f bot
```

Остановить:

```bash
docker compose down
```

### Что нужно до первой команды

1. Скопировать шаблон переменных и заполнить его:

   ```bash
   copy .env.example .env      # Windows
   cp .env.example .env        # Linux / macOS
   ```

2. Вписать в `.env` как минимум `MAX_BOT_TOKEN` (см. раздел 5).

### Запуск без Docker

Если Docker недоступен, бот запускается напрямую:

```bash
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt   # Windows
.venv\Scripts\python bot.py
```

При этом нужен отдельно установленный **Tesseract OCR** с русским языковым
пакетом. Бот ищет его в таком порядке: переменная `TESSERACT_CMD` → папка в
`PATH` → стандартная папка Windows `C:\Program Files\Tesseract-OCR`. Если
Tesseract не найден, бот пишет предупреждение в лог и продолжает работать —
отвалится только разбор фото. База по умолчанию создастся рядом с `bot.py`
как `zhkh.db`.

> **Проверено ли это в Docker.** На машине, где писался этот README, Docker
> не установлен, поэтому образ ни разу не собирался. Состав обвязки проверен
> статически: YAML разбирается, сервис один, секреты не попадают в образ,
> `EXPOSE` отсутствует, точка входа — `bot.py`. Первую сборку стоит считать
> непроверенной и сверять по логу из раздела 13.

## 5. Необходимые параметры окружения

Единственная переменная, без которой бот не запустится вовсе:

| Переменная | Назначение |
|---|---|
| `MAX_BOT_TOKEN` | Токен бота в мессенджере MAX. Выдаётся в кабинете разработчика MAX |

Без него `Bot(token=None)` не сможет обратиться к API. Остальные переменные
не блокируют запуск: бот поднимется и честно предупредит в лог, каких
возможностей ему не хватает.

Чтобы работали **оба** канала — отправка обращений и возврат ответов — нужны
`SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD` и, соответственно,
`IMAP_HOST` с реквизитами. Пароль везде — **пароль приложения**, не основной
пароль ящика.

Реквизиты `IMAP_USERNAME` и `IMAP_PASSWORD` можно не задавать: если они пустые,
подставляются `SMTP_USERNAME` и `SMTP_PASSWORD`.

Полный список с пояснениями — в `.env.example`, подробные инструкции —
в `docs/НАСТРОЙКА_EMAIL.md` и `docs/НАСТРОЙКА_ОТВЕТЫ_УК.md`.

## 6. Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | — | **обязательна.** Токен бота в MAX |
| `DB_PATH` | `zhkh.db` | Путь к файлу базы. В Docker задаётся compose'ом |
| `TESSERACT_CMD` | — | Путь к tesseract, если он не в `PATH` и не в стандартной папке Windows |
| `SMTP_HOST` | — | Сервер отправки, например `smtp.mail.ru` |
| `SMTP_PORT` | `465` | Порт SMTP |
| `SMTP_USE_TLS` | `1` | `1` — сквозное шифрование, `0` — STARTTLS |
| `SMTP_USERNAME` | — | Логин ящика бота |
| `SMTP_PASSWORD` | — | **Пароль приложения** |
| `SMTP_SENDER_NAME` | `ЖКХ-бот` | Имя отправителя в письме |
| `SMTP_SENDER_ADDRESS` | → `SMTP_USERNAME` | Реальный адрес в `From`. Без него письмо невалидно |
| `IMAP_ENABLED` | `1` | `0` — полностью отключить приём ответов |
| `IMAP_HOST` | — | Сервер чтения, например `imap.mail.ru` |
| `IMAP_PORT` | `993` | Порт IMAP |
| `IMAP_USE_SSL` | `1` | `1` — IMAP4_SSL, `0` — обычный IMAP |
| `IMAP_MAILBOX` | `INBOX` | Папка в ящике |
| `IMAP_USERNAME` | → `SMTP_USERNAME` | Логин для чтения |
| `IMAP_PASSWORD` | → `SMTP_PASSWORD` | Пароль для чтения |
| `IMAP_POLL_SECONDS` | `300` | Период опроса ящика, секунд. Меньше 60 не принимается |
| `IMAP_SKIP_EXISTING` | `1` | `1` — при первом запуске пропустить накопленную почту |
| `IMAP_ADMIN_CHAT_ID` | — | Кому отдавать письма без привязки к обращению |
| `GOSUSLUGI_DOM_BOT_URL` | `https://max.ru/gosuslugi_dom_bot` | Ссылка на официальное мини-приложение |
| `RIAS_API_BASE` | `https://api.rias-gkh.ru/v2.0` | РИАС ЖКХ, только чтение |
| `RIAS_API_TOKEN` | — | Токен РИАС ЖКХ. Для чтения реестров, не для подачи |
| `APPEAL_REQUIRE_SIGNATURE` | `0` | Требовать ЭП-подпись в теле письма |

Значения `0`/`1` читаются строго: пишется `1` или `0`, всё остальное считается
выключенным.

## 7. Используемые порты

**Бот не слушает ни одного порта.** Он сам выходит наружу и ждёт ответа в
вызове API MAX (long polling), поэтому в `Dockerfile` нет `EXPOSE`, а в
`docker-compose.yml` нет блока `ports`. Открывать и пробрасывать порты вручную
не требуется — публичный IP и входящие соединения не нужны.

Исходящие соединения:

| Порт | Куда | Режим | Нужен |
|---|---|---|---|
| `465` | SMTP-сервер почты | TLS сразу | Отправка обращения в УК |
| `993` | IMAP-сервер почты | TLS сразу | Приём ответа УК |
| `443` | `api.max.ru` | HTTPS | Работа мессенджера |
| `443` | `api.rias-gkh.ru` | HTTPS | Чтение реестров ГИС ЖКХ |

Если позже включить режим webhook вместо polling (код есть, но закомментирован
в `subscribe_webhook.py`), потребуется входящий HTTPS-порт — сейчас он не
используется.

## 9. Внешние сервисы и интеграции

| Сервис | Роль | Обязателен | Что будет, если недоступен |
|---|---|---|---|
| **API MAX** | Приём сообщений, отправка ответов жителю | Да | Бот не работает: без него нет и входа, и выхода |
| **SMTP** | Отправка обращения в УК | Нет | Обращения создаются, но не отправляются; бот показывает готовый текст письма и ссылки на другие каналы |
| **IMAP** | Чтение ответов УК | Нет | Отправка работает, ответы в чат не возвращаются |
| **Тesseract OCR** | Разбор фото протокола и квитанции | Нет | Сценарии с фото возвращают пустой результат, остальное работает |
| **РИАС ЖКХ** | Чтение реестров: договоры, лицевые счета, ОЖФ | Нет | Сценарии чтения ГИС ЖКХ отключаются, подача обращений работает |

Ни один из необязательных сервисов при падении не роняет бота: отсутствие
настройки фиксируется в лог предупреждением при старте и в статусе конкретного
обращения, а не приводит к аварийному завершению.

Интеграция с ГИС ЖКХ на подачу обращений **не распространяется**: `/appeals` в
этом API — импорт обращений, уже полученных организацией, токен выдаётся
организации. Подробно — `docs/ЖКХ_API.md`.

## 10. Работа с данными

Хранилище — один файл SQLite. В Docker он лежит в bind-mount `./data` и на
хосте виден как `./data/zhkh.db`, его можно открыть обычным просмотрщиком
(`sqlite3`, DB Browser for SQLite) без копирования из контейнера.

Семь таблиц:

| Таблица | Содержит |
|---|---|
| `appeals` | Обращения: адрес, категория, текст, статус, ответ УК, реквизиты, результат отправки |
| `deliveries` | Журнал попыток отправки: канал, адрес получателя, статус, подробности |
| `inbox_state` | Курсор чтения ящика: последний обработанный UID, время проверки, последняя ошибка |
| `profiles` | Профиль жителя: ФИО, адрес дома, свой email, email УК |
| `protocols` | Распознанный текст протоколов и результат проверки подписей |
| `subscriptions` | **Устаревшая.** Подписки удалены, таблица сохранена ради старых данных |
| `meters` | **Устаревшая.** Напоминания о поверке удалены, таблица сохранена ради старых данных |

Правила, которые важно понимать:

- **Миграции только аддитивные.** Новые колонки добавляются через
  `ALTER TABLE ... ADD COLUMN`, новые таблицы — через `CREATE TABLE IF NOT
  EXISTS`. При обновлении **ни одна строка не удаляется**, поэтому
  `subscriptions` и `meters` остаются в схеме, хоть код их больше не читает.
- **Персональные данные минимальны.** Хранится ровно то, что нужно для
  обращения: ФИО, адрес объекта, email заявителя, email УК, текст обращения,
  ответ УК. Лишних идентификаторов не собирается, база локальная.
- **Курсор почты лежит в той же базе** (`inbox_state`, строка всегда одна с
  `id = 1`). Это состояние, а не журнал: после перезапуска или пересоздания
  контейнера бот продолжит с того же места и не пришлёт старые письма повторно.
- **Блокирующий IMAP не трогает базу.** Сетевые вызовы выполняются в отдельном
  потоке через `asyncio.to_thread`, работа с SQLite остаётся асинхронной.

Резервная копия — это просто копирование файла:

```bash
docker compose stop bot
copy data\zhkh.db data\zhkh-backup.db
docker compose start bot
```

## 11. Работа с тестовыми данными

Специального скрипта наполнения в проекте нет, и это осознанно: тестовые
данные удобнее получать настоящим сценарием, а не синтетикой в обход кода.
Ниже — два рабочих способа.

### Способ 1. Пройти сценарий по-настоящему

Самый надёжный тест: довести обращение до письма и обратно.

1. Узнайте свой `user_id` в MAX — вывести его может бот при старте диалога.
2. Впишите его в `IMAP_ADMIN_CHAT_ID` в `.env` (нужно для писем без привязки)
   и перезапустите бота.
3. Напишите боту `/start`, подайте обращение, указав email УК, которым вы
   управляете.
4. Ответьте письмом на `Reply-To` из письма бота — либо напишите в теме
   `Обращение № <номер>`.

### Способ 2. Подложить обращение напрямую в базу

Когда нужно проверить приём ответа, не проходя всю подачу заново. В проекте
есть готовый скрипт — он одинаково работает в Windows, Linux и внутри
контейнера.

Остановите бота, чтобы он не держал базу во время записи:

```bash
docker compose stop bot
```

Создайте тестовое обращение (подставьте свой `user_id` и почту УК, которой
управляете):

```bash
# в контейнере
docker compose run --rm bot python tools/seed_test_data.py --user-id 123456789 --uk-email uk@example.ru

# или на хосте, если бот запущен через venv
python tools/seed_test_data.py --user-id 123456789 --uk-email uk@example.ru
```

Скрипт напечатает номер созданного обращения и готовые следующие шаги.

```bash
docker compose start bot
```

Затем отправьте письмо на адрес УК с темой `Обращение № <номер>` — бот подберёт
обращение по номеру в теме и вернёт ответ в чат.

Скрипт трогает **только свои строки**: их текст помечен словом `TEST-MARKER`,
поэтому обращения жителей не пострадают. Убрать тестовые данные:

```bash
docker compose stop bot
docker compose run --rm bot python tools/seed_test_data.py --clean
docker compose start bot
```

Полезные ключи: `--reset` (удалить прошлый тест и создать новый), `--db путь`
(указать файл базы вручную), `--address`, `--category`, `--full-name`.

Полный сброс — остановить бота и удалить файл:

```bash
docker compose stop bot
del data\zhkh.db
docker compose start bot
```

База пересоздастся пустой при следующем старте.

## 12. Пошаговый сценарий проверки

Ниже — полный цикл от пустого состояния до ответа УК в чате.

**Шаг 1. Подготовка**

```bash
copy .env.example .env
```

Впишите `MAX_BOT_TOKEN`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`,
`SMTP_PASSWORD`, `SMTP_SENDER_ADDRESS`, `IMAP_HOST`.

**Шаг 2. Запуск**

```bash
docker compose up -d --build
docker compose logs -f bot
```

Ожидаемый вывод содержит две строки:

```
... | База данных готова
... | Бот запущен (polling)
```

и предупреждение о планировщике:

```
... | Планировщик запущен: проверка ящика каждые 300 с
```

**Шаг 3. Проверка живости контейнера**

```bash
docker compose ps
```

В колонке `STATUS` должно быть `Up ... (healthy)`. Если `unhealthy` —
сработал healthcheck, и причина в логах.

**Шаг 4. Подача обращения**

Напишите боту в MAX `/start`, затем:

1. «📝 Подать обращение»
2. адрес дома — впишите текстом или нажмите «Использовать сохранённый»,
   если адрес уже был сохранён в профиле
3. выберите категорию кнопкой
4. опишите проблему текстом
5. укажите ФИО, свой email и email УК — кнопкой, если они сохранены

Ожидаемое подтверждение:

```
✅ Обращение №12 отправлено
```

**Шаг 5. Проверка, что письмо ушло**

Откройте почтовый ящик, указанный в `SMTP_USERNAME`. Должно прийти письмо:

- **Тема:** `Обращение № 12 (сантехника) — ул. Мира, д. 1`
  (категория в теме приводится к нижнему регистру)
- **От:** `ЖКХ-бот <адрес из SMTP_SENDER_ADDRESS>`
- **Заголовок `Reply-To`:** адрес ящика бота
- **Тело:** ФИО, адрес объекта, email заявителя, категория, дата, текст,
  подпись и просьба направить ответ в ящик бота

Убедитесь, что в поле `От` стоит **адрес**, а не только имя: без адреса письмо
невалидно и УК не сможет ответить.

**Шаг 6. Проверка истории в боте**

«📋 Мои обращения» — заявка должна быть со сменой статуса и кнопками
«🔄 Обновить статус», «✉️ Отправить заново» и «⚠️ Жалоба в ГЖИ».

**Шаг 7. Ответ УК**

Ответьте на письмо из шага 5 обычной кнопкой «Ответить» в почтовом клиенте —
это самый надёжный вариант, он сохраняет `In-Reply-To`.

Ждать не нужно: вручную нажмите «🔍 Проверить почту сейчас» в разделе
«📬 Ответы УК».

**Шаг 8. Возврат ответа в чат**

Бот пришлёт:

```
📬 Ответ по обращению №12
```

а статус обращения станет «📬 получен ответ».

**Шаг 9. Ошибки вместо молчания**

Если шаг не сработал, бот сообщает причину, а не молчит:

| Сообщение | Что делать |
|---|---|
| «Почта не настроена» | Заполнить `SMTP_*` в `.env` |
| «Ошибка в настройках почты» | Проверить `SMTP_SENDER_ADDRESS` — часто в нём только имя без адреса |
| «Не указан email УК» | Задать email УК в профиле «⚙️ Мои данные» |
| «Ошибка SMTP» | Проверить пароль приложения и порт 465 |
| «Приём писем не настроен на сервере» | Заполнить `IMAP_*` в `.env` |
| «⚠️ Не удалось проверить почту: …» | Смотрите текст после двоеточия — в нём причина отказа IMAP |
| «Не удалось войти в ящик … на imap.mail.ru» | Проверить пароль приложения и включение IMAP у провайдера |

## 13. Ожидаемое поведение системы

Признаки того, что система работает правильно.

**В логах контейнера:**

```
... | INFO | database | База данных готова
... | INFO | bot | Бот запущен (polling)
... | INFO | scheduler | Планировщик запущен: проверка ящика каждые 300 с
... | INFO | uk_inbox | Первый запуск чтения ящика: курсор = UID 1482
... | INFO | uk_inbox | Ответ УК по обращению №12 (appealsbot@mail.ru)
... | INFO | uk_inbox | Проверка почты: ответов 1, нераспознанных 0, пропущено 0
```

**В мессенджере:**

| Событие | Что приходит |
|---|---|
| `/start` | Приветствие и меню из шести пунктов + «🏠 Главная» |
| Подача обращения | «✅ Обращение №12 отправлено» |
| Письмо не ушло | Понятная причина (см. таблицу шага 9) и готовый текст письма |
| Ручная проверка ящика | «📬 Ответов по вашим обращениям: 1 (№12)» либо «Новых ответов на ваши обращения нет» |
| Ответ УК пришёл | «📬 Ответ по обращению №12» с текстом письма |
| Ответ без номера обращения | Ничего или письмо администратору; жителю чужой ответ не придёт |
| Повторная отправка | «✅ Обращение №12 отправлено повторно» |
| Любой экран | Кнопка «🏠 Главная» возвращает в начало |

**В базе данных:**

```sql
-- обращение ушло и получило ответ
SELECT id, status, delivery_status, uk_response IS NOT NULL AS has_reply
FROM appeals ORDER BY id DESC LIMIT 5;

-- журнал отправок
SELECT appeal_id, channel, target, status FROM deliveries ORDER BY id DESC LIMIT 5;

-- состояние курсора чтения ящика
SELECT last_uid, last_check, last_error FROM inbox_state;
```

**Проверка на повторную доставку.** Нажмите «🔍 Проверить почту сейчас» второй
раз подряд. Ответ на одно и то же письмо прийти не должен — это гарантирует
курсор в `inbox_state`.

## 14. Известные ограничения

Ограничения названы прямо, потому что часть из них влияет на юридическую
силу обращения.

1. **Нет прямой отправки в ГИС ЖКХ.** Токен РИАС ЖКХ выдаётся только
   организации, а схема импорта требует идентификатор организации. Подать
   обращение от имени гражданина через API нельзя. Ограничение подтверждено
   АО «Оператор ГИС ЖКХ» 21.01.2026: обращения, созданные вне ГИС ЖКХ,
   невозможно корректно связать с личным кабинетом жителя без идентификации
   через Госуслуги.

2. **Обращение не связано с личным кабинетом в ГИС ЖКХ.** Из-за этого по
   обращению нельзя отследить статус в ЛК. Срок ответа — до 30 дней
   (ст. 12 59-ФЗ) — приходится ждать письма, а не смотреть в кабинет.

3. **Без электронной подписи обращение юридически ничтожно.** По ст. 7 59-ФЗ
   требуется идентификация заявителя. По умолчанию подпись не требуется, иначе
   обращения перестали бы отправляться; переключается переменной
   `APPEAL_REQUIRE_SIGNATURE`. Юридически чистый канал — «Госуслуги Дом»
   с авторизацией через Госуслуги, ссылка на который есть в карточке
   обращения.

4. **Привязка ответа УК ненадёжна, если УК ответит не из того письма.** Бот ищет
   обращение тремя способами по убыванию надёжности: `In-Reply-To` /
   `References` → номер обращения в теме или в тексте → иначе письмо
   считается неопознанным. Если не сработало ни то, ни другое, письмо **не
   угадывается**: оно попадает в журнал и, если задан `IMAP_ADMIN_CHAT_ID`,
   администратору — но не случайному жителю.

5. **Опрос ящика не в реальном времени.** По умолчанию раз в 300 секунд, плюс
   одна проверка сразу при старте бота. Период меньше 60 секунд не
   принимается. Пока бот остановлен, ответы не забираются — они накопятся и
   придут в чат после запуска.

6. **Точность OCR зависит от фото.** Плохое освещение, блики, мелкий шрифт и
   сложный рукописный протокол распознаются плохо. Для критичных проверок
   оставлено ручное подтверждение и честная оговорка в ответе бота.

7. **Данные не шифруются на уровне приложения.** SQLite лежит открытым файлом
   в bind-mount и защищён только правами файловой системы. Это неприемлемо для
   промышленной эксплуатации: нужен шифрованный том и ограничение доступа.

8. **Вебхука нет.** Работа только через long polling. При большой нагрузке
   polling менее выгоден, чем приём вебхуков; код приписки есть, но закомментирован
   в `subscribe_webhook.py`.

9. **Один экземпляр.** Планировщик не защищён от повторного запуска: при
   двух процессах опрос ящика пойдёт дважды. Для одного инстанса проблемы нет.

10. **Docker-обвязка не проверена сборкой** на машине, где писался этот README.
    Состав проверен статически, но первая сборка требует ручной проверки по
    логу из раздела 13.

11. **Таблицы `subscriptions` и `meters` пустуют.** Код их больше не читает,
    они оставлены в схеме, чтобы ранее сохранённые данные не пропали.

## 15. Остановка и повторный запуск

### Обычная остановка

```bash
docker compose stop bot
```

Контейнер останавливается, **данные сохраняются**: они в bind-mount `./data`
вне контейнера. Это предпочтительный способ — после `stop` тот же контейнер
поднимается с тем же состоянием.

### Полное удаление

```bash
docker compose down
```

Удаляет контейнер и сеть. Файл `./data/zhkh.db` **остаётся на диске** —
удалять нужно руками и осознанно.

### Повторный запуск

```bash
docker compose start bot
```

Контейнер поднимается за секунды, образ не пересобирается. Бот при старте
выполняет опрос ящика сразу, не дожидаясь первого тика планировщика, и
продолжает с курсора, сохранённого в `inbox_state`.

Если код или зависимости изменились — пересборка:

```bash
docker compose up -d --build
```

### Перезапуск после сбоя

Политика `restart: unless-stopped` поднимает бота автоматически после падения
контейнера и после перезагрузки хоста. Но после перезагрузки **сам Docker
может не стартовать** — тогда бота нужно поднять вручную:

```bash
docker compose start bot
```

### Обновление без потери данных

```bash
docker compose down
docker compose up -d --build
docker compose logs -f bot
```

Миграции аддитивные, поэтому обновление не требует бэкапа для сохранности
данных. Бэкап всё же стоит сделать, если в базе появились реальные обращения
жителей: `copy data\zhkh.db data\zhkh-backup.db`.

### Полный сброс состояния

Нужен, когда проверяете поведение с нуля:

```bash
docker compose down
del data\zhkh.db
docker compose up -d
```
